VB6-x64 IDE
PLAN DE DESARROLLO TÉCNICO POR MILESTONES
Versión 1.0 — MVP: abrir, leer y editar proyectos VB6 clásicos en Windows x64
============================================================================

1. OBJETIVO
-----------
Construir un IDE para Windows x64 inspirado en Microsoft Visual Basic 6.0. La
primera versión debe abrir proyectos VB6 existentes, navegar sus archivos y
editar código sin convertirlos a otro formato ni corromper el diseño visual.

El IDE se desarrollará en paralelo al compilador VB6 Open Compiler x64, pero
ambos deben permanecer desacoplados. El IDE podrá abrir y guardar código aunque
el compilador y el runtime todavía no existan.

MVP: FUNCIONES INCLUIDAS
- Abrir un proyecto .vbp.
- Mostrar los elementos del proyecto en un Project Explorer.
- Abrir y editar .bas, .cls y código de formularios .frm.
- Resaltado sintáctico VB6.
- Pestañas, guardar, guardar como, deshacer/rehacer, buscar/reemplazar.
- Avisos de cambios no guardados y copias de seguridad configurables.
- Conservación de codificación, saltos de línea y recursos no editados.

FUERA DEL MVP
- Compilación, ejecución y hot reload.
- Depurador.
- Diseñador visual editable.
- Reimplementación de controles VB6.
- Conversión automática o reformateo del proyecto.

Los controles x64 serán una fase posterior. No son necesarios para leer y editar
código. La primera prioridad es abrir, editar y guardar sin alterar archivos que
el usuario no ha modificado.

2. ARQUITECTURA TÉCNICA RECOMENDADA
-----------------------------------
IDE:
    C# + WPF, dirigido a Windows x64, sobre .NET 10 LTS.
Editor de código:
    AvalonEdit, componente WPF con licencia MIT; crear reglas propias para VB6.
Integración futura:
    API, CLI o servicio independiente (por ejemplo JSON-RPC/LSP) para recibir
    diagnósticos y símbolos del parser/compiler cuando estén disponibles.

Referencias oficiales:
    WPF / Windows Desktop:
    https://learn.microsoft.com/en-us/dotnet/desktop/
    .NET 10:
    https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-10/overview
    AvalonEdit:
    https://github.com/icsharpcode/AvalonEdit
    Scintilla, alternativa de editor:
    https://www.scintilla.org/ScintillaDoc.html

Que el IDE esté escrito en C#/.NET NO significa que las aplicaciones VB6-x64
compiladas deban depender de .NET. El IDE, el compilador y el runtime son
componentes distintos.

3. REGLAS FUNDAMENTALES DE SEGURIDAD
-----------------------------------
1. No reescribir archivos que el usuario no modificó.
2. No convertir ANSI a UTF-8 de forma silenciosa.
3. No cambiar CRLF/LF sin autorización.
4. No reconstruir completamente un .frm para guardar solo un cambio de código.
5. No abrir ni guardar archivos .frx como texto: contienen datos binarios.
6. Preservar líneas desconocidas del .vbp y referencias que aún no se soporten.
7. No borrar elementos desconocidos del proyecto.
8. Abrir o editar no debe ejecutar código.
9. Cada Milestone tendrá pruebas automatizadas y fixtures reales.
10. No declarar compatibilidad total con VB6 sin pruebas demostrables.
11. No activar compilación/ejecución en el MVP.
12. Si la codificación es ambigua, permitir configurarla y advertir; no fingir
    que siempre puede detectarse automáticamente sin error.

MILESTONE 2 — MODELO DE DOCUMENTO Y LECTURA/GUARDADO SEGURO
============================================================================
Objetivo: poder leer y guardar texto VB6 sin cambios involuntarios.

Crear EditorDocument con campos conceptuales:
    FilePath, DisplayName, Text, Encoding, HasByteOrderMark,
    NewLineConvention, IsDirty, IsReadOnly, OriginalHash, LastSavedHash.

Tareas:
2.1 Detectar BOM de UTF-8 y UTF-16.
2.2 Para archivos sin BOM, admitir la página de códigos ANSI de Windows y una
    opción de codificación por documento/proyecto.
2.3 No asumir que Encoding.Default equivale a la página ANSI del sistema en
    todas las versiones de .NET; consultar explícitamente la ACP si se necesita.
2.4 Registrar el tipo de salto de línea CRLF, LF o CR.
2.5 No reescribir un archivo que no haya sido modificado.
2.6 Implementar guardado temporal + reemplazo controlado.
2.7 Crear copia .bak antes de sobrescribir, según configuración.
2.8 Detectar cambios externos ocurridos mientras el documento estaba abierto.
2.9 Avisar de conflictos de escritura y respetar el atributo de solo lectura.
2.10 Mantener el hash/tamaño/fecha que se usará para pruebas de integridad.

Pruebas obligatorias:
- ANSI, UTF-8 con/sin BOM y UTF-16.
- CRLF y LF.
- Caracteres acentuados.
- Archivo de solo lectura.
- Modificación externa en disco.
- Abrir/cerrar sin editar y comprobar que el archivo no cambió byte a byte.

Terminado cuando las pruebas verifican que los archivos no modificados no se
reescriben y que los modificados siguen las reglas definidas.

MILESTONE 4 — RESALTADO SINTÁCTICO VB6
============================================================================
Objetivo: destacar sintaxis VB6 sin alterar el texto.

Categorías iniciales:
- Palabras reservadas.
- Tipos de datos.
- Comentarios con apóstrofo y Rem.
- Strings con comillas dobles y comillas dobles escapadas.
- Literales numéricos.
- Literales de fecha delimitados por #.
- Operadores y puntuación.
- Atributos/directivas reconocibles.

Tareas:
4.1 Definir reglas y colores de sintaxis VB6.
4.2 Crear pruebas de strings, comentarios, continuaciones y operadores.
4.3 Asegurar que las palabras dentro de strings no se resaltan como keywords.
4.4 Implementar tema claro/oscuro como configuración.
4.5 Diferenciar claramente resaltado de sintaxis de análisis semántico.

Terminado cuando los ejemplos se muestran correctamente y el resaltado no
altera el documento.

MILESTONE 7 — EDICIÓN SEGURA DE FORMULARIOS .FRM Y RECURSOS .FRX
============================================================================
Objetivo: editar el código de formularios sin corromper su diseño.

Advertencia técnica:
Un .frm contiene información serializada del formulario/controles, propiedades,
atributos y código. Puede apuntar a recursos binarios guardados en un .frx.
No se debe tratar el .frm como si fuera solamente un .bas ni reconstruirlo
completo a partir de un modelo parcial.

Tareas:
7.1 Recopilar formularios de prueba guardados por VB6 SP6.
7.2 Estudiar y delimitar la sección de código frente a la sección serializada.
7.3 Mantener intacta la parte de diseño original.
7.4 Guardar sustituyendo únicamente el tramo de código editado.
7.5 Preservar atributos de módulo y líneas desconocidas.
7.6 No actualizar offsets ni referencias .frx desde el editor de código.
7.7 Nunca abrir un .frx en el editor de texto.
7.8 Si no se puede identificar la región modificable con seguridad, abrir .frm
    en solo lectura y mostrar un aviso explícito.
7.9 Comparar el .frm antes/después y confirmar que no cambió el diseño.
7.10 Confirmar que los .frx no cambiaron byte a byte.

Terminado cuando formularios de prueba pueden editar su código sin alterar
involuntariamente los controles, propiedades o recursos.

MILESTONE 12 — DISEÑADOR EDITABLE Y CONTROLES X64
============================================================================
Fase posterior: no comenzar antes de estabilizar apertura y guardado.

Objetivo: editar formularios y crear controles compatibles con el runtime x64.

Tareas:
12.1 Definir contrato de cada control: propiedades, eventos, valores por
     defecto, persistencia y ciclo de vida.
12.2 Separar modelo de diseño de la interfaz del IDE.
12.3 Definir una biblioteca de controles x64 para el runtime.
12.4 Priorizar controles intrínsecos:
     Form, Label, TextBox, CommandButton, CheckBox, OptionButton, Frame,
     ListBox, ComboBox, PictureBox, Image y Timer.
12.5 Implementar propiedades y eventos de forma incremental.
12.6 Mantener correspondencia de nombres, por ejemplo Command1_Click.
12.7 Implementar serialización .frm solo para los casos conocidos.
12.8 Preservar propiedades/líneas desconocidas del archivo.
12.9 Crear pruebas de apertura y guardado que incluyan VB6 SP6.
12.10 Probar por separado diseñador, controles y runtime.

Advertencia:
Un proceso x64 no puede cargar directamente DLL/OCX de 32 bits. Los ActiveX
clásicos de 32 bits requerirán sustitución por componentes x64 o un puente entre
procesos. No intentar cargarlos directamente dentro del proceso x64.

Terminado cuando un subconjunto documentado de formularios puede editarse,
guardarse y, en el futuro, ejecutarse con el runtime x64.

============================================================================
MILESTONE 13 — INTEGRACIÓN DE BUILD TRADICIONAL (FUTURO)
============================================================================
No forma parte del MVP.

Objetivo: integrar compilación y ejecución normal cuando el compilador esté
listo, generando primero un ejecutable en disco.

Reglas:
- No ejecutar código sin compilarlo.
- No implementar hot reload/hot execution.
- Build debe producir salida verificable.
- Run debe ejecutar el EXE construido, no interpretar directamente el fuente.
- Los errores deben enlazar con archivo/línea/columna cuando sea posible.
- Build/Run deben ser opcionales y desacoplados del editor.

Terminado cuando las acciones utilizan un compilador real, documentado y
probado. No simular compilación si no existe.

============================================================================
Crear fixtures con:

- Referencias/componentes desconocidos.

- CRLF y LF.
- Archivos .frm vinculados a .frx.

Comprobar:
- Los archivos no editados permanecen byte a byte idénticos.
- Los .frx nunca cambian al editar código.

- No se eliminan líneas desconocidas de .vbp.
- Se detectan conflictos y documentos modificados.
- Abrir/editar nunca ejecuta el programa.
- No hay comandos de Build/Run funcionales en el MVP.
